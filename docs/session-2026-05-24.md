## Fixes shipped

### Regrow → Expand loop boundary (the headline bug)
- `scene/event_catalog.py` — `RegrowAction._pin_grown` now bails out when
  an *absolute* non-regrow modulator on `radius` or `alpha` was created
  at or after this regrow started. Additive ops (Pulse) don't trigger the
  bailout. New tests in `test_sequential_events.py::TestRegrowFollowedByExpand`.

### Dissolve "garbage" — fade snapped backward when alpha changed
- `DissolveAction._begin_fade` now reads `state.alpha` **live** inside
  the callback rather than capturing it at `on()` time. A pulse or other
  alpha change during the disperse/float phases no longer causes a fade
  ramp dip. New tests in `test_animation_correctness.py::TestDissolveFadeBaseValue`.
- Same pattern in `DissolveAction.on` — disperse mod's base is the live
  `state.dissolve_amount` so it ramps smoothly from wherever the scene was.

### Per-event defaults (color, ease, density) for MIDI playback
- New `router.set_event_default(name, params)` + matching API:
  `GET / PUT /api/scene/event_defaults` and `/api/scene/event_defaults/{name}`.
- Param precedence in router dispatch: `event_defaults` < `lane.params`
  < per-trigger `params`.
- Admin Events row persists color / ease / extra-param changes via the
  new endpoint. Loaded into the UI on boot + on patch swap.
- Patches save/load includes `event_defaults`.

### Palette editor surfaces all 8 slots
- `admin.js::PALETTE_COLOR_KEYS` extended to include `color4..7`.
- Palette bank gradients now span all 8 colors (Tune tab + Scene tab).
- Editing a slot refreshes the gradient + the FX event-color dropdown
  swatches without rebuilding the editor.

### MIDI piano roll: zoom-fit on load (cap at 8 bars)
- `admin.js::zoomFitWithCap(8)` — fits the whole loop unless > 8 bars,
  in which case it caps the visible window. Called on init + sequence load.

### Scene.set_animation cleanup
- Now clears `_active_sfx`, `_active_pushes`, `_active_pull`,
  `_active_torques`, `_scheduled` in addition to mods/baselines. Fixes

### Palette commit callback tagged

## Iteration 14 (dissolve rethink + tails + MIDI auto-fit fix)

User: "Dissolve is still a total mess. Jerky. Rethink it: start from
fast spinning following the circles, particles diverge from orbits,
slow down, settle in brownian, fade. Tails: longer, inertial like a
kite tail ribbon."

Big creative rewrite of the dissolve animation:

- **Orbital speed inverted** (`scene/animations/synth.py::_render_dots`):
  was `0.6 * (1 - dissolve_amount) * motion_speed` (~0.15 rad/s at
  start — barely visible). Now `orbit_speed_max * (1 - dissolve_amount)^1.5`
  with default `dot_orbit_speed = 4.0` (rad/s), quadratic falloff.
  At the start of a dissolve, particles ZIP around the rings like
  comets; the orbital motion slows quadratically as dispersal grows
  and stops at full dispersal. The fast-spin phase now reads visually
  before the brownian-cloud phase takes over.

- **Phase split rewritten** (`scene/event_catalog.py::DissolveAction`):
  was 30% disperse / 30% float / 40% fade with ease-OUT (fast scatter
  at start — the "jerky" feel). Now 70% disperse / 10% float / 20%
  fade with ease-IN — dissolve_amount stays low for most of the
  animation so the spinning-comets phase has time to read; the
  dispersal accelerates toward the end. Settle/fade are faster.

- **Tail length + ribbon feel** (`scene/animations/synth.py`):
  - `trail_steps` default 14 → 28 (double the tail length).
  - `trail_dt` default 0.08 → 0.07 (slight closer spacing so 28
    samples don't smear into a continuous line).
  - Tail spacing formula changed from `trail_dt * dissolve_amount`
    (tail invisible at low dissolve_amount, "explosion at the start")
    to `trail_dt * (0.3 + 0.7 * dissolve_amount)` — tail VISIBLE
    from the start (30% spacing) so the spinning-comets ring reads;
    grows to full ribbon length as dispersal completes. Tail is now
    a "ribbon" trailing the head with delay; head turns → tail
    follows after `k * effective_dt` seconds. Default tail span
    grows from ~1.12 s (old) to ~1.96 s (new).

- **MIDI auto-fit on reload** (`admin/static/admin.js`): the
  init-time `zoomFitWithCap(8)` was bailing because the MIDI tab is
  `display:none` on first load (wrap.clientWidth = 0). Now also
  called from `_activateTab("scene")` via `requestAnimationFrame` so
  the fit runs the moment the tab becomes visible. Closes the
  user's "MIDI editor doesn't auto-set to fit on reload" report.

- Updated `TestDissolveFadeBaseValue` tests for the new 70/10/20
  phase timing (was 30/30/40).

Total: 221 tests, all green on dev. Pi: mode=scene fps=29.7.

## Iteration 30 (admin page TDZ crash + dissolve perf + motion model)

2. **Dissolve/Respawn dropped FPS to 8** during 3-oval dissolve.
   Each oval was rendering its own full dot cloud — 3× the work.
   Fix: render the dot cloud only for the TOP oval (i=1, drawn last
   in our `(0,2,1)` ordering = middle). Visually nearly identical
   but 3× the perf. Combined with reducing defaults (`dot_count`
   16→12, `trail_steps` 22→14): FPS during dissolve went 8 → 24-28.

3. **Particle motion was "lateral" — head sliding sideways via
   brownian noise**. User asked for forward-only motion: head
   always moves in its heading direction; the heading turns
   smoothly; tail follows with inertia. Fully rewrote the dot
   simulation as a stateful particle system:
   - `SynthAnimation` now owns `_dots_xy`, `_dots_heading`, and a
     ring-buffer `_dots_trail` of past positions per particle.
   - `tick()` advances each particle: heading += turn_rate × dt;
     position += (cos(h), sin(h)) × speed × dt. At low
     dissolve_amount, turn_rate ≈ orbital ω (perfect circle). At
     high dissolve_amount, turn_rate adds smooth pseudo-random
     wander.

     (heading flips inward + small twist so they don't ping-pong).
   - Ring-buffer trail = literal past positions. Tail follows the
     head's actual path with delay; head turns → tail arrives at
     the turn later. True ribbon inertia.
   - Particles spawn lazily on first dissolve, free when
     dissolve_amount returns to 0.
   - The old functional renderer is kept as `_render_dots_legacy`
     (unused) for reference; tests updated to use the stateful one.

## Iteration 31 (dissolve/respawn redesigned per user's sketch)

Per the user's hand sketch: dissolve should have 3 visible stages —
**circles → diverge → random+fade**. The previous design just
crossfaded a ring rendering with a particle field; the user wanted
the *particles themselves* to form/unform the rings, with a smooth
inertial transition.

**New design (Reynolds-style steering)**:

- Each particle assigned round-robin to one of the 3 rings (outer /
  middle / inner). Each has stateful `(x, y, heading)` + ring index +
  ring radius.
- Tick computes a **target heading** = orbital tangent at the
  particle's current angular position on its ring, plus a small
  radial correction if it has drifted off-radius.
- Heading update: `h += diff_to_target × steer_strength × dt
                       + wander_noise × wander_strength × dt`
  where `steer_strength = (1−dissolve_amount)² × 8` and
  `wander_strength = dissolve_amount^1.5 × 5`.
- Position update: `(x, y) += (cos h, sin h) × speed × dt` — always
  forward, no lateral teleporting.
- Soft boundary at 1.8× outer ring reflects heading toward center on
  contact (with small random twist to avoid ping-pong).

So at `dissolve_amount = 0`: max steering → particles are pinned to
their ring tangents → particles ARE the rings.
At `dissolve_amount = 1`: zero steering → free wander → particles
scattered, each on its own path.

**Lifecycle hooks**:
- `DissolveAction.on()` now calls `anim.spawn_particles_on_rings(state)`
  before starting the disperse modulator — so particles begin
  indistinguishable from the rings (no pop-in).
- `RespawnAction.on()` calls `anim.spawn_particles_random(state)` —
  particles start scattered with random headings, then converge as
  `dissolve_amount` ramps 1→0.

**Ring visual handoff**: `ring_weight = (1 − dissolve_amount)³`
(was linear `1 − d`). Ring rendering drops to ~5% by d=0.6, gone by
d=0.7. Particles' contribution is now full intensity throughout
(removed the `× dissolve_amount` multiplier) — they're indistinguishable
from the ring at low d, then become the only visible element as the
ring fades.

**Particle fade-out**: relies on the existing `state.alpha`
multiplier at end of `render()`. Once `_pin_dark` fires at 80% through
the dissolve, alpha ramps to 0 over the fade phase → particles
naturally disappear.

Pi: dissolve fps 22-26, respawn fps 25-30 (climbs to 30 as
particles lock onto rings). Smooth across the entire animation.

## Iteration 32 (two-parameter orchestration)

Per user feedback ("we need two parameters: how fast particles are
moving and how close the motion is to circular orbit — the animation
is a careful orchestration of these over time"):

**Two new state keys** driving the particle motion:

- `dot_speed` (0..1) — multiplies BASE_SPEED (30 LED/sec). At 1.0
  particles whip around the rings visibly (~1 rev / 1.5 s on r=8).
- `dot_orbit_lock` (0..1) — steering strength toward orbital tangent.
  1.0 = locked to ring (particles ARE the rings). 0.5 = wandering
  but biased toward circular motion. 0.0 = pure forward wander.

These replace the implicit `(1-dissolve_amount)²` derivation from
iter 31. The motion no longer depends on dissolve_amount at all —
that variable is now ONLY for the renderer's ring-weight crossfade.

**DissolveAction** now creates 4 modulators with multi-point envelopes:

```
dissolve_amount: 0 → 1 over 70% of total (existing ease-in disperse)
dot_orbit_lock:  [(0,1), (0.15,1), (0.40,0.55), (0.70,0.10), (1,0)]
                  hold lock for 15%, diverge through middle, settle
                  to wander
dot_speed:       [(0,1), (0.20,1), (0.50,0.85), (0.75,0.40), (1,0.20)]
                  fast spin holds for 20%, then slows
alpha:           1 → 0 over last 20% (existing fade)
```

So the visible phases are:
1. Particles spin FAST on rings (15-20% of total)
2. Diverge from rings while still fast
3. Slow down, wander randomly
4. Alpha fade to black

**RespawnAction** reverses it:

```
dot_orbit_lock:  [(0,0), (0.30,0.15), (0.60,0.55), (0.85,0.95), (1,1)]
                  wander → curving → snap into orbit
dot_speed:       [(0,0.25), (0.40,0.50), (0.75,0.90), (1,1)]
                  slow drift → speed-up → full orbital
alpha:           0 → 1 over first 30% (existing fade-in)
dissolve_amount: 1 → 0 over 100% (rings fade in as orbit_lock → 1)
```

Phases:
1. Slow random wander (alpha low)
2. Speed climbs, particles start curving toward orbits
3. Snap into orbital lock, rings fade in
4. Particles on rings, full speed, full lock = visible spinning rings

The user's mental model maps directly to the code: each modulator is
one "parameter envelope" in the orchestration. Editing the dissolve/
respawn feel is now a matter of tweaking 4-5 control points per
envelope.

Pi: dissolve fps 23-28, respawn 23-30 (climbs to 30 as orbit_lock
locks in and steering math simplifies).

## Iteration 33 (speed-from-lock + aggressive ease curves)

User feedback:
> "I'd derive the speed from the snap param. The closer to the orbit,
>  the faster it moves. Then animate it using some easing curve. Btw,
>  our pre-set curves should be a tad bit more aggressive — I barely
>  notice the difference on real animations."

**Speed derived from orbit_lock** (`scene/animations/synth.py::tick`):

```
speed = BASE_SPEED × dot_speed_mult × (MIN + (MAX-MIN) × orbit_lock^EXP)
```

Defaults: `BASE_SPEED=36`, `MIN=0.10`, `MAX=1.30`, `EXP=1.6`. So at
orbit_lock=1 particles move ~47 LED/s (clearly visible spinning);
at orbit_lock=0 they drift at ~3.6 LED/s (slow random wander).
EXP=1.6 gives a "slow to start, accelerates as it locks in" feel —
the snap-into-orbit moment is pronounced.

DissolveAction and RespawnAction no longer emit a separate dot_speed
modulator (removed `dissolve-speed` / `respawn-speed`). The
orbit_lock envelope alone now drives both the steering strength AND
the visible speed, halving the modulator count and keeping the two
parameters intrinsically synchronized (you can't accidentally have
high speed + low lock or vice versa).

Three new admin sliders expose the curve for tuning: **Speed Min**
(0..1), **Speed Max** (0.3..2.5), **Speed Curve** (0.3..4 — the
exponent).

**Ease curves made more aggressive** (`scene/envelopes.py`):

| Label        | Was            | Now              |
|--------------|----------------|------------------|
| ease_in      | t² (quad)      | t³ (cubic)       |
| ease_out     | 1-(1-t)²       | 1-(1-t)³         |
| ease_in_out  | cosine         | smootherstep (6t⁵-15t⁴+10t³) |

At t=0.5: ease_in_quad gives 0.25, cubic gives 0.125 — twice as
"held back" at the midpoint. The 5th-order smootherstep is much
steeper through the middle than cosine. User-set curves on per-event
ease pickers + on Dissolve/Respawn now feel like deliberate shapes
instead of "linear with a slight curve".

Pi: dissolve fps 25-28 (unchanged). Bumped admin.js to v=56.
